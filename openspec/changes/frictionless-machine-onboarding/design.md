## Context

Onboarding a daemon today requires the human to visit the **Machines** tab, type a
label, click **Add machine**, and copy a per-machine access key that the UI shows
**once**. The key then travels by hand to `flexitracker configure --key <KEY>` on the
target machine. Two problems: the copy/paste is error-prone and the key is
irrecoverable if missed.

Structurally, `machine_id` today is a random UUID minted **per key**
(`registry.ts:359` `issueKey`) — there is no durable notion of "the machine called
Work laptop." That conflation blocks the follow-up `per-machine-worktime` proposal,
which needs a stable machine identity to attribute and filter history by.

Constraints that shape this design:
- **Two-realm auth is load-bearing**: humans authenticate with Google via Cloudflare
  Access; daemons hold a write-only per-machine key. The daemon must never touch
  Google credentials.
- **Zero cost, forever**: Workers + Durable Objects + D1 only; no paid or trial
  primitives, no new dependencies.
- **All Cloudflare infra changes go through version-controlled scripts + GitHub
  Actions** (`provision-access.yml`), never dashboard clicks; QA-vs-PROD is derived
  from hostname inside the provisioning scripts.
- **Fail fast**; the daemon is stdlib-only pure Python managed with `uv`.

## Goals / Non-Goals

**Goals:**
- A `flexitracker login [--name]` command that authorizes a daemon with **zero
  secret copy/paste** — the user authenticates in a browser and the key lands in
  `config.toml` directly, never displayed.
- A first-class, durable **Machine** entity distinct from the access key, with a
  stable `machine_id` that survives key rotation and hardware replacement.
- Enforce **one active key per Machine** so two daemons cannot corrupt span pairing.
- Make the **Machines tab optional** for onboarding.
- Collapse the daemon command surface to `login` + `test`, removing `configure`;
  preserve the manual paste-a-key path as `login --key` (fed by "Add machine").

**Non-Goals (deferred to `per-machine-worktime`):**
- Per-machine weekly view, multi-select, and the `counts_as_work` flag.
- Adding `machine_id` to `daily_rollup`/`session` and union-at-read.
- A device-code (RFC 8628) headless flow — noted as a future `--headless` fallback,
  not built here.
- Machine grouping/tags.

## Decisions

### D1. Loopback redirect over device-code (RFC 8628)
The `login` flow binds a listener on `127.0.0.1:<ephemeral port>`, opens the browser
to `/device/authorize?...&cb=127.0.0.1:<port>&state=<nonce>`, and the backend
redirects the approved result back to the loopback callback. This is the
`gh auth login --web` / `wrangler login` pattern.

- **Why over device-code**: loopback needs **no server-side polling loop and no
  pending-state store to be strongly consistent under polling** — the handshake is a
  single request/redirect/exchange. It is the smoothest UX on a laptop (the target
  machine has a browser, which is the norm for a flextime tracker).
- **Trade-off**: requires a browser *on* the machine being registered — breaks on a
  truly headless/SSH box. Accepted for v1; device-code is the documented future
  `--headless` escape hatch.

### D2. Exchange a one-time authorization code, not the key, over loopback
The backend redirects to the loopback callback with a **short-lived, single-use
authorization code**; the daemon then calls `/device/token` to exchange the code for
the actual access key. The key never appears in a URL (not even a loopback one),
limiting exposure to other local processes that might observe loopback URLs.

- **Alternative considered**: redirect the key directly. Simpler, and the threat
  model already treats the key as low-value write-only — but the code indirection is
  cheap and keeps the secret out of URLs, so we take it.
- A random `state` nonce generated by the daemon and echoed by the backend guards
  against a stray/forged callback; the daemon rejects a mismatched `state`.

### D3. Access topology: `/device/authorize` protected, `/device/token` bypassed
`/device/authorize` is a **browser path protected by Cloudflare Access** — this is
where Google login happens, preserving the two-realm split (the daemon opens a URL;
Access + Google do the rest; the daemon never sees credentials). `/device/token` is
a **non-browser path Access-bypassed** like `/ingest` and `/whoami`, authorized
instead by the one-time code. This is a `provision-access.yml` +
`setup-access-bypass.mjs` change, with QA-vs-PROD derived from hostname.

- **Known-pitfall guard**: an un-bypassed `/device/token` would return the Access
  **login HTML (HTTP 200)** that parses to `{}` — the classic "unexpected `{}` from a
  JSON fetch = a login redirect on a non-bypassed path." The provisioning must land
  before the flow is exercised; Access config propagates asynchronously (re-run
  before assuming a logic bug).

### D4. Pending-auth state in D1 (or the account DO), never KV
Whatever minimal server-side record the exchange needs (the pending authorization
code → account/label/machine binding, with an `expires_at` and single-use flag)
lives in the **strongly consistent** D1 registry (or a Durable Object). KV's
eventual consistency (edge lag) would let a just-approved code read stale, breaking
the exchange. Loopback keeps this record tiny and short-lived; a cleanup deletes
expired codes.

### D5. Machine as a first-class entity; key binds to it
Introduce a durable Machine identity `{ machine_id, account_id, label, ... }`. Key
issuance changes from "mint a new `machine_id` per key" to "resolve or create a
Machine, then bind a key to its `machine_id`." Resolution is **by (account, label)**:

```
login --name "Work laptop"
  └─ resolve Machine(account, "Work laptop")
       ├─ none          → create Machine (new machine_id)     → issue key
       └─ exists         → reuse machine_id
             ├─ its key revoked/absent → issue key (seamless continuation)
             └─ its key ACTIVE + recent → REQUIRE explicit replace-or-separate (D6)
```

The registry gains a Machine concept alongside `machine_key`. The DO-side `machine`
table already keys on `machine_id`; the registry becomes the source of truth for the
label ↔ machine_id mapping so a key can bind to an existing machine. (`ensureKey`
reuses the whole *key* by label — that is fixtures behavior; here we want a **new
key, same machine_id**, so this is a distinct code path.)

### D6. One active key per Machine; explicit replacement in the browser
Issuing a key for a Machine that already has an active key **revokes the prior key in
the same operation**. Because the human is already in a browser during `login`, the
approval page is the right place to disambiguate the "old laptop still running" case:
if the target Machine has an active, recently-seen key, the page shows the conflict
and last-seen time and forces a choice — **replace** (revoke prior key) or **create a
separate machine** (new machine_id). No silent kill. This invariant is what protects
`pairSpans()` sequential per-machine span pairing from interleaved events, and it is
required precisely *because* label reuse (D5) is introduced.

### D7. One `login` verb, not `login` + `configure`
Authorization is a single command with the browser flow as the default and a
`--key` escape hatch (`gh auth login` / `gh auth login --with-token` shape), leaving
`test` as the only other daemon command. `configure` is **removed outright**, not
kept as a deprecated alias — the project is pre-release with no users, so there is
nothing to break, and two sibling authorization verbs would be incoherent. The
manual paste path (`login --key`) and the web "Add machine" button survive as the
headless/scripted fallback until the device-code `--headless` flow lands.

## Risks / Trade-offs

- **Loopback needs a local browser** → device-code `--headless` fallback is designed
  for later; `login --key` (paste a key from "Add machine") remains today for
  headless/scripted boxes.
- **Access propagation delay for `/device/token`** → the classic `{}`-login-page
  failure; mitigate by provisioning ahead of use and re-running before assuming a
  bug (matches the documented Access-propagation pitfall).
- **Loopback URL observable by other local processes** → mitigated by exchanging a
  one-time code (D2), binding only to `127.0.0.1`, a `state` nonce, and short code
  TTL. Residual risk is low and bounded (write-only key, revocable).
- **Accidental replacement revokes a live daemon** → mitigated by the explicit
  browser confirmation (D6); replacement is never silent.
- **Label collisions across intent** ("Work laptop" typed twice for two real
  machines) → the replace-or-separate choice covers it; picking "separate" yields a
  distinct machine_id.
- **Registry ↔ DO machine-table consistency** → the registry owns label ↔ machine_id;
  the DO `machine` row is still self-registered on first ingest keyed by the same
  `machine_id`, so the two agree by construction.

## Migration Plan

1. **Backend, additive first**: add the Machine model + label-based resolution to the
   registry (new machine_id only when no label match); keep `issueKey` callers
   working. Existing keys keep their current `machine_id` (each is effectively its
   own single-key Machine) — no data migration of historical events needed.
2. **Add `/device/authorize` (protected) + `/device/token` (bypass) routes.**
3. **Provision Access**: extend `setup-access-bypass.mjs` + `provision-access.yml`
   for `/device/token`; dispatch and verify propagation.
4. **Daemon**: replace `configure` with the `login` command (browser default +
   `--key` manual form) + loopback listener (stdlib `http.server`, `webbrowser`,
   `secrets`); `test` unchanged. No `configure` alias is kept (pre-release, no users).
5. **UI**: add the login approval page (+ replacement conflict); make onboarding
   present `login` as recommended, `login --key` as fallback; Machines tab →
   view/rename/revoke.
6. **QA e2e**: extend fixtures/smoke to exercise the device flow end-to-end (mint via
   `/device/*`, verify one-active-key-per-machine, verify label reuse keeps
   machine_id). Green QA e2e auto-promotes to PROD.
- **Rollback**: the browser flow is additive on the backend; the daemon-side fallback
  is `login --key` fed by the "Add machine" button, which stays available.

## Open Questions

- Exact approval-page trust affordance: show requesting IP / rough geo alongside the
  machine label to help the human judge an unexpected request?
- Authorization-code TTL and the loopback attempt timeout (target ~a couple of
  minutes for the whole approve-and-exchange window).
- Whether renaming a Machine from the Machines tab should be a plain label edit
  (identity unchanged) — assumed yes; confirm no key rotation is implied by a rename.
- QA fixtures: does the `/test/*` bypass harness need a device-flow shortcut, or is
  exercising the real `/device/*` endpoints preferable (matches "synthetic events
  flow through the REAL pipeline")? Leaning real endpoints.
